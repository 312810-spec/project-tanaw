## 2. Identity and atomic imports: use an explicit mapping layer

The inspected CO roster stores names in INPUT DATA K11:K60 and N11:N60, without a verified learner key. A row number, name hash or name match cannot become an official learner identity. The workaround is a coordinator-reviewed mapping against an authorized roster: workbook slot + school/class/subject/term → stable school learner key. An LRN need not be publicly exposed or embedded in filenames. Duplicate/ambiguous matches block the whole batch; roster revision and mapping revision belong in its manifest. This mapping design is proposed, not implemented or approved.

Separate operations into preparation and commit. Preparation validates source/version, identity mapping, score bounds, exact discrepancies and complete coverage. Commit is one server database transaction, bound to request identity, current ownership/version, deadline/extension/amendment and Lock. Repeating the same request must reconcile its recorded result rather than create duplicate versions. Existing manual submission/reconciliation controls remain the behavior reference.

Raw-file storage and a database transaction are **not** one cross-service transaction. Stage the immutable private file first, identify it by school/batch/hash, then atomically commit its verified reference with all evidence/version rows. Failed staging creates no accepted evidence; failed commit leaves an unaccepted staged object for attributable reconciliation/cleanup. Never call a partially imported roster successful. This is a proposed implementation contract, not a tested import RPC.

Primary technical references: PostgreSQL transaction semantics, https://www.postgresql.org/docs/17/tutorial-transactions.html ; Supabase private buckets and RLS, https://supabase.com/docs/guides/storage/buckets/fundamentals and https://supabase.com/docs/guides/storage/security/access-control . Public buckets bypass read access controls and are unsuitable for class records. DO 015, printed page 14/PDF page 17, specifies supporting-record retention for at least one school year, longer for audit/validation/appeals, with controlled/logged access in official or authorized systems. A school retention/hosting decision is still required; no deletion schedule or approval is invented.

## 4. Governed results and exports: build contracts with synthetic values first

**Implementation can proceed without fake official data.** Use locked packet manifests and exact submission versions as the only result inputs. Define every aggregate through a verified dictionary/contract: result ID, unit, population, period, permitted method, required contributions, overlap rules, rounding and definition version. For ratios, sum matching evidenced numerators and denominators; averaging class percentages is not equivalent. Enrollment snapshots cannot be summed across terms without a defined population rule. Zero counts remain distinct from absent contributions.

The proposed projection should return unavailable/incomplete with coverage/reason metadata when required inputs or semantics are missing. A source-traceable output can identify contribution versions without exposing names, LRNs, raw scores, freeform private source notes or class-record files. District routes must fetch only that projection with school/district authorization; successful arithmetic alone does not permit raw-data disclosure. Existing district acceptance stays disabled until the projection, frozen versions, required reviews and privacy tests pass.

Create synthetic template adapters against a selected layout before actual records arrive: explicit target cell/slide/field mapping, typed units, source version, editable chart bindings and incomplete state. Keep label/shape fidelity separate from content authority. Until current templates and semantics are confirmed, an internal working projection or mapping preview must be labelled accordingly; it cannot be presented as an approved SMEA report. Do not fabricate an Excel/PPT/PDF official output to make a blocker appear resolved.

Acceptance scenarios for the next slice: recorded zero; one missing contribution; duplicate population; overlapping scope; denominator zero; mixed school/year/term; stale definition; superseded submission; incomplete locked packet; amendment creates a new projection; denied district raw-data fetch; repeated request returns the same committed result. These are proposed tests; the real result/export slice is not implemented by this research increment.

## 5. Coordinator provisioning and SMTP: separate bootstrap from normal use

Supabase's default email service is a development mechanism: current documentation restricts recipients to project-team addresses and lists a two-per-hour default limit. It cannot support ordinary staff recovery without custom SMTP. Do not work around this by sharing service credentials, disabling identity verification under pressure or inventing confirmed accounts.

Keep local Mailpit/CI synthetic recovery tests as the verified development route. For operational use, select the school's authorized SMTP sender, configure the exact trusted origin/callback and verify delivery to a designated consenting test account. Provider selection, sender/domain approval, credentials and actual receipt are external inputs; this session did not create a subscription, send email or mutate hosted settings.

Initial coordinator bootstrap is a separate server-only operator action for a designated identity. Normal provisioning should authenticate an active school coordinator, enforce school/scoped role rules on the server, create/invite the Auth account with protected server credentials, then grant membership using a resumable audited request. Auth API creation and database membership insertion are separate operations; a failure must leave an account without unintended school access and support safe retry. Never self-grant from client metadata. This is an architecture contract, not a shipped provisioning endpoint.

Primary references: https://supabase.com/docs/guides/auth/auth-smtp and https://supabase.com/docs/reference/javascript/auth-admin-createuser . The createUser documentation explicitly restricts it to server use and prohibits exposing the service key in the browser. TANAW's existing hosted-operation approval rules continue to apply.
